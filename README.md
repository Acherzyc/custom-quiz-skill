# 自定义刷题 · 题库转换 Skill (quiz-bank-converter) v2.3

> 把任意格式的考试资料（PDF 讲义、真题集、扫描件、图片、Word、表格）通过**绝对视觉识别**转换为《自定义刷题》微信小程序标准题库 JSON。
> PDF 默认全部渲染后视觉直读；只有整份 PDF 完全可读取时才允许直接读原生文本，坚决不使用 OCR。

---

## 🚀 快速使用

1. 把 PDF 资料路径发给 Agent，发送：
   > *"使用《自定义刷题》规范 v2.2，帮我把这份资料转成题库 JSON，科目=言语理解，题库名=专项练习"*
2. Agent 自动：渲染页面 → 视觉识别 → 跨页拼接 → 答案表校验 → 结构化 JSON → 交付。

## 🆕 v2.3 修正了什么

**填空位（原文横线）统一写作 6 个半角下划线 `______`。**

小程序渲染层只认「≥2 个连续半角下划线」，识别后由 CSS 画一条固定长度的横线；写错字符就直接失效：

| 写法 | 小程序里的结果 |
|---|---|
| `______`（6 个半角） | ✅ 正常画出横线 |
| `_`（1 个） | ❌ 认不出，横线凭空消失 |
| `＿`（全角） | ❌ 认不出，退化成字体渲染，不同机型表现不一 |
| `__ __`、`_ _` | ❌ 被空格隔断，当英文单词处理 |
| 下划线后带空格/换行 | ❌ 断行，横线脱离句子 |

v2.3 把这条写成硬规则（SKILL.md §5.4 + §6.3），并进了交付前自检脚本：全角下划线、数量不是 6、前后带空格/换行，任意一条命中就报错。原图上横线印得再短（半角 4 个宽就是极限），输出一律补齐 6 个。

> 为什么不用全角下划线来"加宽"：全角字符不在识别范围内，交给字体会重现「下划线变点 / 直接没线」的老 bug。线宽是小程序样式层的事，不该由数据里的字符来凑。

## 🆕 v2.2 修正了什么

- **「无答案」处置**：资料里没有答案的题不再建议写成 `answer:"待确认"`（会被小程序校验器拦截、导致整卷导入失败），改为**不写入 questions 数组** + 列入交付报告的待确认清单，待补答案后单独成批补交。
- **交付前自检脚本改为类型感知**：`judge/fill/essay` 不再被误判为「缺选项」，`single/multiple` 校验 2–10 项。

## 🆕 v2.1 改了什么

基于 165 页扫描讲义实战转换经验，修复了三个实际踩坑：

| 问题 | v2.0 | v2.1 |
|---|---|---|
| **跨页续文误判为新题** | 无规则，165页中产生15道重复题 | §3.3：有无题号判定续文vs新题 |
| **答案对错无校验** | 只说"视觉比对" | §6.1：答案表字母计数 = 转录题数 |
| **顶层字段写错** | 只列了字段名 | §5.2：name≠title红线表，交付前自检脚本 |

## ⚡ v2.2 提速与准确率改进

- 默认所有 PDF 先渲染页面并视觉识别；仅“整份完全可读取的纯文本 PDF”可走文本例外。
- 扫描件、混合 PDF、双栏错序和复杂版面统一走视觉路径；疑难页局部提高渲染 DPI。
- 按题目边界分批并保存页码/题号进度清单，支持断点续跑。
- 置信度低、答案冲突、题号断档时仅回看对应页，避免重复通读。
- 坚决不调用或安装任何 OCR；交付前使用类型感知校验，避免把 judge/fill/essay 误当缺选项。
